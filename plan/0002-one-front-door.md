## Context

Intent 0002 (accepted 2026-11-02): running the loop is clunky because intents start in a terminal while the board lives on Netlify, and every hand-off between the two is a seam someone must know. Spec 0002 (accepted 2026-11-03; R1–R20; 27 design-gate concerns resolved) makes the board a front door that acts as the signed-in person, gives the terminal the same view (`/flow`), keeps the hand-off copy in one place, and measures done with a counted trial by a second person holding the engineer role. Decisions already made: gate 5 off the board; no refresh tokens; no required code-owner review (known gap); `/new` in; plan lives in `fernhill-flow`; automation path out.

Exploration found three facts the spec did not know, resolved below: `scripts/validate-artifacts` now requires `commit` on every release record (PR #12), so the "proposed record precedes the secrets" rule needs `commit` optional while `proposed`; the template is one sync behind the platform (no record-hold step, stale `/review`); and a `roles` edit in `flow.config.json` is mergeable today under a plain `merge` grant, which breaks R13 until the hook learns a never-delegable check.

## Contracts frozen early

- **`next-steps.json`** (platform): `{ "<state>": { "text": string, "command"?: string, "href"?: "<template>", "noClone"?: true } }` keyed by the derive states (`plan.decide`, `design.spec-open`, `design.no-spec`, `build.no-repo`, `build.no-plan`, `build.plan-proposed`, `test.ci-red`, `test.review`, `test.not-reviewed`, `deploy.approve`, `deploy.failed`, `maintain.triage`, `action.flip-waiting`, `action.refused.*`, `board.off`, `exception.regrant`, `preview`). The engine renders `{repo}`, `{number}`, `{id}`, `{clone}`; skills quote the `text` verbatim after `Next:`.
- **Roles**: platform `roles.json` = `Record<RoleKey, string[]>` (collected beside `flow.config.json` and carried in the snapshot as `config.roles`), `RoleKey = product_owner | engineer | code_owner | release_manager | on_call`; engine `ROLE_KEY: Record<Role, RoleKey>`. Grant→role: `merge`, `merge-guardrails` → `code_owner`; `flip-status` → `product_owner`; `approve-plan` → `engineer`; `release` → `release_manager`.
- **Exception holders**: flat frontmatter keys `holders_<role_key>: [login, …]` (line-based parsers in the validator, the hook and the workflow all read them unchanged); they are the source, and the prose `role:` line becomes informational.
- **Session cookie** `flow_session`: AES-GCM-256 over `{ sid, login, token, exp }` (`sid` random 16 bytes) with IV 96-bit random, AAD = the site host (`fernhill-flow.netlify.app`, `main--…`, `spike--…` are distinct), key = `SESSION_KEY` (base64, 32 bytes, one per context); `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age ≤ 8h`. `flow_state`: random 32 bytes, `SameSite=Lax`, 10 min. CSRF token = HMAC(`SESSION_KEY`, `sid`) exposed by `/api/me`, required in `X-Flow-CSRF` on every `POST /api/act`. The refresh trigger `action` is honoured only with a valid session cookie; otherwise it is treated as `manual` (floor applies).
- **`POST /api/act`** body `{ action, repo, number?, payload? }`; responses `200 { done, next }`, `409 { refused, next }`, `401`, `403 (role)`, `503 (no snapshot/config)`; header `X-Flow-Action: 1`.
- **Schema 2**: `Snapshot.config` carries `roles`, `board_actions`, `github_app`, `next_steps`; `Pr` carries `reviews: { by, state, verdicts }[]` for open build PRs, where `verdicts` is parsed from the bounded full body (the `Fernhill review` header and each persona's closing line), never a truncated head; `Plan` carries `headSha` and `onMain`; `RepoSnapshot.codeowners: { ok, drift: string[] }`.

## Risks

- **Riskiest: the App acting as a person against GitHub.** Permission intersections, auto-merge (repo setting on; `check` must run on the flip commit), and branch protection could each refuse. De-risked in step 1 on the `spike` branch deploy with a throwaway endpoint, before anything depends on it; `docs/baseline-auth.md` records what GitHub actually required. Fallback if auto-merge is unavailable: the row stays two-step with the waiting copy (already specified). Mid-way rollback: P1 merged with no product change leaves the live board as it is (v0.1's `validateConfig` ignores unknown files and keys); PR A alone ships a board identical for signed-out visitors; PR B rolls back by publish-previous, with v2 snapshots read by v1 code as absent.
- **Cross-repo generation.** The validator can only write files in a local checkout; product `CODEOWNERS` are checked by the collector at refresh and written by `new-product` and `sync-template`. Drift shows on Systems rather than failing CI in the product. Accepted and stated in flow.md.
- **Secrets ordering.** The record must exist before the secrets; `commit` optional while `proposed` makes that possible. The release-hold step in `release.yml` matches `commit == sha`, so a record without `commit` never releases by accident.
- **`roles` in its own file.** `roles.json` makes the never-delegable rule a path check in the hook, a `CODEOWNERS` line and a validator rule, with no diff inspection; the spec said `flow.config.json` and is amended in P1 (recorded departure).
- **Action → refresh latency.** Trigger `action` skips the 60 s floor but respects the single-flight lock, so two people acting at once still produce one collection; the row shows the waiting copy until the refresh lands.
- **Schema bump.** v1 blobs are treated as absent and refreshed; fixture mode boots because `sample.json` is bumped in the same commit; previous snapshot is not preserved across the bump (one-time).
- **The second person does not exist yet.** Steps 0–7 need only the product owner; the roles PR and the trial wait for them. If none is named by release, the record stays `proposed` and 0002 stays in Deploy on the board — which is the truth.
- **Rejected:** a server-side write token or App private key (every function becomes a route to `main`); an OAuth App instead of a GitHub App (no per-repo installation, no expiring tokens); refresh tokens; required code-owner review now (deadlocks owner-authored PRs); server-side derivation for the board (kept in the browser; only `/api/next` runs the engine in a function); a Blobs session store (nothing about a person stored); one product PR (eight steps and six new functions is too much to review at once; the schema step is shippable on its own); hunk inspection of `flow.config.json` for `roles` (false negatives when context lines hide the block); a header-controlled `action` trigger (anyone could skip the floor).
